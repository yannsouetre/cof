## BLOCKING

### F1 — Explicit media reachable through `media_from` from a non-explicit node, including in a minor preset
- **Where**: RFC 0002 § 4.5 ("`media_from` … inherits nothing else"), § 5.3, § 6.1; `validate.py` `_memory_rules` (l. 1083–1111, 1160–1183), `_asset_age_rules` (l. 931–945), `model.variant_asset_ids` (l. 307–315).
- **What**: `media_from` is excluded from `variant_asset_ids`, so the borrowing node is invisible to every 1.0 asset rule (nude asset used by a non-nude variant, asset shared across ages, "intimate files are its own"). `_memory_rules` only looks at `node.explicit`, which the RFC says is *not* inherited. Reproduced: fixture `m3` set to `explicit: intimate` + `nudity: true` + `tags.content`, `m4` left as is (`media_from: memories/m3`, no `explicit`, no `nudity`, no `age`), a new preset `child` (`age_override` 12) listing only `m4` → **zero errors, zero warnings**. A 12-year-old preset therefore carries an intimate image, reachable by any reader that follows `media_from` (`memories.effective_media` does).
- **Fix**: (a) in the RFC, state that `explicit`, `nudity: true` and the age requirement are *not* inheritable and that a node whose effective media (through `media_from`, transitively) come from an explicit node MUST itself be `explicit` with the same value and `nudity: true` (error otherwise); (b) in the validator, compute effective media before the nude/age rules and include them in `variant_asset_ids` (or a memory-specific equivalent) so the 1.0 rules fire; (c) add the negative case.

### F2 — An explicit node with nobody declared `shown` and no variant `age` validates in any adult preset
- **Where**: RFC 0002 § 5.2, § 5.4 ("Every person shown in an explicit memory must have a known age ≥ 18 … an unknown age never counts as adult: the file is invalid"); `validate.py` l. 1134–1170; `_age_rules` l. 986–993 (`carries` excludes `memories`).
- **What**: all age checks are keyed on `who[].shown`. An explicit node whose `who` is absent (or has no `shown` entry) and whose variant has no `age` passes with `nudity: true` + `tags.content` alone. Reproduced on the fixture (`m3`: `explicit: intimate`, `who` removed, variant `age` removed) → **zero errors, zero warnings**. By definition an explicit media shows a person, so "unknown age never counts as adult" is not applied here.
- **Fix**: for an explicit node, require at least one `shown` person (self or other), and require the variant `age` ≥ 18 whenever the node is explicit (treat an explicit node like `appearance/intimate`: `age` always required). State it in § 5.4 and § 6.1 and add the negative case.

### F3 — RFC 0003 says *warning*, the validator and the CHANGELOG say *error* for 1.1 fields in a `cof: "1.0"` file
- **Where**: RFC 0003 § 6: "a `cof: "1.0"` file that uses any of these fields: warning "this file uses 1.1 fields; declare `cof: "1.1"`" (1.0 readers ignore them anyway)"; `validate.py` l. 263–274 (`rep.errors.append("cof 1.0 declared but the file uses 1.1 additions …")`); `test_cast_rules` l. 1097–1101 asserts an **error**; CHANGELOG l. 6 "a 1.0 file using these fields must declare 1.1"; RFC 0002 § 6.1 and § 7 make the same situation an **error** for memories.
- **What**: the two RFCs disagree with each other and RFC 0003 disagrees with its own reference implementation. The rule "a file declares the lowest minor that defines everything it uses" (RFC 0002 § 7, manifest schema `cof` description) has one severity.
- **Fix**: make RFC 0003 § 6 say "error", same wording as RFC 0002 § 6.1, and drop the parenthesis "(1.0 readers ignore them anyway)" or move it to § 8 as the reason the error is harmless to readers.

### F4 — § 4.5 contradicts itself on how a shared media is declared, and the validator accepts only one of the two forms
- **Where**: RFC 0002 § 4.5: "MAY be referenced by one memory node of each character shown, **either by listing it in the variant's `media`** or with the variant field `media_from`" and, three lines later, "The exception exists **only through this field**, so it is easy to find and to check." `validate.py` `_character_rules` l. 883–890.
- **What**: listing the same asset in `media` of two characters' nodes is an error in a cast file ("asset … is used by several characters … but memories.<v> (moment) is not neutral"), because `memories` is never neutral and `variant_asset_ids` includes `media`. Only `media_from` escapes that rule. The first sentence of § 4.5 is therefore false against the implementation.
- **Fix**: delete "either by listing it in the variant's `media` or"; say that `media_from` is the only way, and that a second `media` listing is the 1.0 error.

## SHOULD

### F5 — Which field makes a memory enter the preset's age: § 5.2/§ 5.4 say `when.age`, everything else says the variant `age`
- **Where**: RFC 0002 § 5.2 "A node with media showing the character carries an age (`when.age`), and that age enters the preset's lowest age"; § 5.4 "the character through `when.age`"; vs § 3 table (`age` on the manifest variant), § 4.1, § 6.1 ("a node whose media show the character without a variant `age`"); `model.preset_age`/`variant_ages` read the **variant** `age` only; `validate.py` l. 1153–1158 only *warns* when the two differ by more than 0.5.
- **What**: the normative text names a field the code never reads for the minor rule. With `when.age: 15`, variant `age: 18`, `explicit: nudity`, self shown: the file validates with a warning only.
- **Fix**: in § 5.2 and § 5.4 name the variant `age` as the field that counts (mirrored from `when.age`), and make a mismatch an **error** on explicit nodes (a warning elsewhere).

### F6 — `explicit: intimate` with a real person only requires consent scope `nudity`
- **Where**: RFC 0002 § 5.5 "consent record carries `nudity` or `intimate`"; `validate.py` l. 1178 (`{"nudity", "intimate"} & set(scope)`); SPEC § 7 "an `intimate` variant requires `intimate` (error); a variant marked `nudity` requires `nudity` or `intimate`".
- **What**: a real person in an `intimate` memory passes with `nudity` consent alone, which is weaker than the 1.0 rule for `appearance/intimate`.
- **Fix**: `explicit: intimate` → scope `intimate` required; `explicit: nudity` → `nudity` or `intimate`. Say so in § 5.5.

### F7 — "A memory *about* a real person" rules are only enforced for memories *owned by* a real person
- **Where**: RFC 0002 § 4.2 `factual` ("a validator warns for every memory of a real person without it"), § 5.5 ("A memory about a real person requires that identity's consent scope `conversational-persona` … and `factual`"); `validate.py` l. 323 (owner only), l. 1185 (owner only).
- **What**: a fictional character's memory with `who: [{ "identity": "marc" }]` where `marc` is `fictional: false` triggers neither the `conversational-persona` check nor the `factual` warning. "Of" and "about" are used interchangeably in the RFC and only "of" is implemented.
- **Fix**: define both: *owned by* a real person → `conversational-persona` on the owner + `factual`; *naming* a real identity in `who` → `conversational-persona` on that identity (warning). Implement the second.

### F8 — Membership and `after` rules: the RFC's canonical example trips its own warning, and the rule is stated three ways
- **Where**: RFC 0002 § 3.2 (`after`: "Order when `when` does not settle it (undated nodes). Contradicting `when` on both sides: warning"; `part-of`: "the link is for exceptions … Contradiction: a coherence finding"); § 4.3 ("bounds inclusive … Clara's first morning in the studio, at 28, is `after` the agency years 24–28: the ages touch, the link decides"); § 6.1 warnings ("`after` contradicting dates"), coherence ("`part-of` contradicting dates"); § 6.5 builder check "a moment outside its period"; CHANGELOG l. 11 "An `after` link to a period that contains the moment by dates is a finding (the link wins)"; CHANGELOG l. 10 (explorer) first says ev2 at 28 sits "under the agency years 24–28" by dates, then says an `after` link is never nested.
- **What**: (1) with inclusive bounds, 28 is inside 24–28, so example 10's `ev2 after ep1` is exactly the case § 6.1 flags as a warning and § 3.2 reserves for *undated* nodes; (2) § 3.2 calls `part-of` on an in-range moment an exception, while § 4.3/§ 6.5 make `part-of` the only thing a preset chip follows — so authors will add it to every moment (example 10 does: `ev9`, `ev10` are `part-of ep2` while inside its 27–29 range); (3) "deliberately out-of-range" is a sanctioned use of `part-of` (§ 3.2) yet "contradicting dates" is flagged (§ 6.1); (4) none of the "`after` contradicting dates", "different birth years", "`part-of` contradicting dates" findings exist in `cof-cli` (`grep` finds no such code; `memory-timeline` appears only in the RFC), and `docs/coherence-api.md` does not list a `memory-timeline` check although § 6.2 says it gains one.
- **Fix**: define precisely: *inside* = `start ≤ point ≤ end` on the same axis; `after P` contradicts dates iff `point < end(P)` (so touching bounds are fine) — or make `after` exclude the end bound; say `part-of` is the normal way to attach a moment a preset chip must follow and dates are the display fallback (or the reverse, but one of them); say "out-of-range `part-of` is informational, never a finding"; either implement the three findings in `cof-cli` or move them from § 6.1 "Warnings" to "implemented by the builder; the coherence API is a contract". Add `memory-timeline` to `docs/coherence-api.md` or drop the claim in § 6.2. Fix CHANGELOG l. 10's first sentence.

### F9 — `isolated in the node's own folder` is neither enforced nor compatible with § 4.5 / § 5.5
- **Where**: RFC 0002 § 5.3 "The three consequences of the 1.0 opt-in … extend to memory media: never loaded by default …, **isolated in the node's own folder**, flagged"; § 5.5 "several consenting real identities of one file may share memories of a scene"; `validate.py` l. 958–965 (folder rule only for `appearance/intimate`).
- **What**: a shared explicit media (via `media_from`) lives in one node's folder and is used by another node; the validator never checks memory folders at all.
- **Fix**: either drop "isolated in the node's own folder" for memories (say: the media of an explicit node are used by no non-explicit node, see F1), or enforce the path rule and state that `media_from` is the one tolerated cross-folder use.

### F10 — `tags` are "free strings" in the RFC but ASCII-lowercase in the schema
- **Where**: RFC 0002 § 3 table "`tags[]` | Free strings (objects, events, public figures…)"; `memory.schema.json` `tags.items.pattern: "^[a-z0-9][a-z0-9:-]*$"`; `selfdesc.memory_add` slugs (`Léo` → `leo`).
- **What**: `"Été"`, `"Miss Tral"`, `"grand-mère"` fail the schema; the RFC never says tags are slugs. Example 10 happens to comply.
- **Fix**: say in § 3 "slug: lowercase ASCII, digits, `-` and `:` (as `tags.*` in 1.0); builders slug what the author types", or relax the pattern.

### F11 — `who` entry cannot carry both `identity` and `label`
- **Where**: RFC 0002 § 4.2 "`who` — list of `{ identity: "self" | <cast id> }` or `{ label }`"; `memory.schema.json` l. 113–124 (`oneOf` required identity / required label).
- **What**: `{ "identity": "martien", "label": { "fr": "le Martien" } }` fails with an opaque `oneOf` message; a display label for an identity entry is a natural thing to write, and the RFC text ("or") does not read as "exclusive".
- **Fix**: either say "exactly one of" in the RFC, or change `oneOf` to `anyOf` and let `label` be a display override. Also say what `real: true` means on an `identity` entry (the schema allows it; the RFC says the identity decides; the validator ignores it).

### F12 — `max_bytes_ack` is read at the root; the schema and 1.0 put it on the variant
- **Where**: RFC 0002 § 4.1 "the 1.0 cap of `motion` videos (20 MB unless `max_bytes_ack`) applies"; `validate.py` l. 1108 `manifest.get("max_bytes_ack")`; `manifest.schema.json` l. 749 (`max_bytes_ack` is a **variant** property).
- **What**: an author who sets `max_bytes_ack: true` on the memory variant (the only place the schema defines it) still gets the warning; a root key is undefined.
- **Fix**: read `rv.get("max_bytes_ack")`; say in § 4.1 "on the memory variant, as on a `motion` variant".

### F13 — `revisions` on a node without `origin` is not caught although the default is `authored`
- **Where**: RFC 0002 § 3.3 "Validators are silent on an absent field (the default applies)"; § 6.1 warning "`revisions` on an `authored` node"; `validate.py` l. 1190 `node.get("origin") == "authored"`.
- **What**: the default is not applied when evaluating the rule; the same pattern is used for `visibility` (fine, default `canon`) and `disclosure`.
- **Fix**: `node.get("origin", "authored") == "authored"`. Same for `nature` where used.

### F14 — Gist "absent or empty" is only half-checked
- **Where**: RFC 0002 § 6.1 errors "`gist` absent or empty"; `memory.schema.json` (`minProperties: 1`, values `string` with no `minLength`); `_memory_rules` l. 1070–1073 (length only).
- **What**: `{"gist": {"en": ""}}` validates.
- **Fix**: `minLength: 1` on the `text` values (or an explicit validator error).

### F15 — Unresolved `who[].identity` and cross-character `where.environment` are only checked when `identities` exists
- **Where**: RFC 0002 § 6.1 errors "unresolved … `who[].identity`", "`where.environment` across characters"; `validate.py` l. 1136 (`and ids and`), l. 1129 (`elif ids and`).
- **What**: in a single-character file with no `identities` table, `who: [{"identity": "bob", "shown": true}]` passes; `bob` is then an unknown person of unknown reality.
- **Fix**: when `ids` is empty, only `"self"` is a valid `identity` (error otherwise).

### F16 — RFC 0003 `mutual` is underspecified and the "two sides disagree" check ignores it
- **Where**: RFC 0003 § 3 "`mutual` (boolean, default true for symmetric types) says the other side holds the same relation"; `cast.relations_of` l. 196 (`mutual is False` suppresses the computed inverse for **all** types), `cast_rules` l. 155–166 (no look at `mutual`); manifest schema (no default).
- **What**: (1) no default is stated for asymmetric types, and "the same relation" is meaningless for `parent`→`child`; (2) what `friend` + `mutual: false` means (a one-sided friendship?) is not said; (3) `A: friend→B, mutual: false` with `B: enemy→A` is reported as "the two sides disagree", which the author declared on purpose.
- **Fix**: either drop `mutual` from 1.1 (nothing in the examples uses it) or define it as "compute the inverse" with default `true` for every type, and skip the disagreement check when `mutual: false`.

### F17 — Relation `label` is copied onto the computed inverse; whose point of view is it?
- **Where**: RFC 0003 § 3 "`label` a language map (the sentence that matters)"; `cast.relations_of` l. 201 copies `label` and `since` onto the inverse; `identity_lines` l. 253 prints `Name — type (label)`.
- **What**: with the test fixture (`Léo: child → Clara, label "sa mère"`), Clara's SOUL.md reads "Léo — parent (sa mère)": the label was written from Léo's side. `since` ("in the subject's life", an age) is likewise copied to the other subject, for whom the age is wrong.
- **Fix**: say the label is written from the subject's side and is **not** carried to the inverse (or is carried with a marker "as declared by X"); never copy `since` when it is an age.

### F18 — "Stored once" for symmetric types is stated as a rule but a second copy is silently accepted; `other` has no inverse
- **Where**: RFC 0003 § 3 "Symmetric types … are **stored once**, on either side"; § 6 duplicate rule is per identity only; `relations_of` dedupes `(to, type)`; `INVERSE` has no entry for `other`, so `relations_of` never shows an `other` relation from the other side.
- **Fix**: say "SHOULD be stored once; a copy on the other side is merged (not an error)"; say `other` is never inverted (the other character does not see it) or invert it as `other` with the same label.

### F19 — RFC 0003 coherence "a relation `since` after the subject's age in a preset" is not implemented anywhere
- **Where**: RFC 0003 § 6 Coherence; `cof-cli` has no code reading `since` except to copy it (`cast.py` l. 201); the builder's `index.html` has no such check either.
- **Fix**: implement (cheap: `since.age` vs `preset_age`) or move to § 9 open questions.

### F20 — RFC 0003 fields live only in `identities.<id>`; a root-only 1.0 file has nowhere to put them, and `identity_view` ignores the root copy
- **Where**: RFC 0003 § 3 (identity fields), § 8 ("a 1.0 reader sees nothing"); SPEC § 2.1 (`identities` is optional: "a file **can** describe a cast"; the root carries the single character's `name`, `nickname`, `summary`…); manifest schema root properties (no `gender`, `given_name`…); `cast.identity_view` l. 79 (`identities` only) vs `model.preset_identity` l. 224 (falls back to the root copy).
- **What**: a single-character file without an `identities` table cannot declare a gender except by adding `identities` + `default_identity` + the root mirror; the RFC never says so. `identity_view` returns `{}` (or the bare override) for such a file, so `export_soul` l. 278 then falls back to `preset_identity` and loses any `identity_override`.
- **Fix**: state in § 3 that these fields are defined on `identities.<id>` only and that a root-only file introduces the table (the builder always does); make `identity_view` fall back to the root copy like `preset_identity`.

### F21 — `export --agent` has no real-person guard, unlike `extract --identity`
- **Where**: RFC 0002 § 4.5 guard ("when a character is extracted … media that show another real person are dropped"), § 5.7 ("`cof extract`, `cof export` and any sharing path drop [personal nodes]"); `convert.export_agent` l. 446–452 copies every media of non-explicit nodes through `media_assets` (follows `media_from`), with no call to `shows_other_real_person`.
- **What**: the agent workspace carries no consent records at all, so the reasoning of § 4.5 applies with more force to the export than to the extract; a cast file exported for Clara ships Marc's likeness.
- **Fix**: apply `strip`-equivalent logic in `export_agent` (skip media where `shows_other_real_person(…, {owner})`) and say in § 6.4 that the § 4.5 guard applies to the agent export.

### F22 — `cof memory add --media` writes media with no `who`, no `age`, no `real` flag; the "never add a memory that shows a real person" rule is prose only
- **Where**: RFC 0003 § 7, RFC 0002 § 3.3 ("Everything that happens in use is a layer of `lived` nodes"), `selfdesc.memory_add` l. 138–155, COF.md l. 59 ("Never add a memory that shows a real person who is not a consenting identity of this file").
- **What**: the one write path hosts are told to use cannot express "this photo shows the user" or "this shows the character"; the node it writes passes every validator rule (nothing is `shown`), so a host that drops a selfie of the user into a lived memory produces a valid file with an undeclared real person. The AI age check (§ 5.6) is a coherence-API contract, not part of `cof memory add`.
- **Fix**: add `--who-self-shown --age N` and `--who "<label>" --shown --real` options (or refuse `--media` images without a `who` declaration), and list "declare who is shown" in COF.md step 2. Alternatively state in § 5 that a lived node with image media and no `who[].shown` is a **warning** ("nobody declared shown").

### F23 — `drop_personal_memories` deletes a folder whose files may still be referenced
- **Where**: `ops.drop_personal_memories` l. 358–370: when a canon node borrowed a personal node's media via `media_from`, the list is copied onto the canon node (`ov["media"] = med`), then `shutil.rmtree(elements/memories/<personal>)` removes the files those asset paths point to; `_prune_assets` keeps the manifest entries because they are "still used".
- **What**: the result is a manifest that references missing files (an invalid extract) — the opposite of what the comment intends. Also a questionable design: a user's personal media becoming canon media of another node.
- **Fix**: either move the borrowed files into the borrowing node's folder and rewrite the asset paths, or drop the media from the borrowing node too (as `_memory_media_off` does for the explicit purge) and say so in § 5.7.

### F24 — Reference-implementation and example claims that do not match the branch
- **Where**: RFC 0002 § 7 "Example: `spec/examples/10-clara-mercier` becomes the first 1.1 file, with **five memories and fifteen media**: four moments … and one period … **The eight other examples stay 1.0**"; RFC 0002 § 4.1 "the builder names moments `ev<n>` and periods `ep<n>`" vs § 6.5 "a fixed code (`m1`, `p2`…)" (the fixture uses `m1`/`p1`, the example and `memory add` use `ev`/`ep`); § 7 "Negative corpus: one case per error of § 6.1"; RFC 0002 header "cof-cli 1.1.0 (validator …)" with § 6.1 warnings that are not in the validator (F8).
- **What**: example 10 holds 16 nodes (14 moments, 2 periods, including an alternate "AI war" line and a manga restyle) and 30 memory-media assets; example 11 is a 1.1 file (RFC 0003 § 8) so "the eight other examples stay 1.0" is false; `tests/invalid/cases.json` holds 12 memory cases for ~17 error rules in § 6.1 (missing: unresolved `media` / `media_from` / `where.environment` / `who[].identity`, cycle, cross-character environment, `part-of` on a non-moment, `revisions` with media, `explicit` without matching `tags.content` as a separate case) and no RFC 0003 case at all; the code prefix is stated twice with different values.
- **Fix**: update § 7 (counts, "seven other examples"), pick one id convention (`ev`/`ep`) in § 6.5, soften "one case per error" to what exists or complete the corpus, and make § 6.1 list only what `cof validate` does (move the rest to § 6.2/§ 6.5).

### F25 — Manifest schema `relations[].since` is looser than the RFC's "point as in RFC 0002 `when`"
- **Where**: RFC 0003 § 3; `manifest.schema.json` l. 1854–1868 (`date` pattern `^-?\d{1,4}(-\d{2}(-\d{2})?)?$`, no `label`); `memory.schema.json` `$defs/date` (month `0[1-9]|1[0-2]`, day `0[1-9]|[12][0-9]|3[01]`).
- **What**: `"since": {"date": "2026-13-45"}` validates on the identity but the same string fails in a memory node; the two "point" grammars drift.
- **Fix**: use the same pattern (or a shared `$defs/point` in the manifest schema) and allow `label` if "as in `when`" is meant literally.

### F26 — Normative MUSTs that no tool can check are not identified as author/tool obligations
- **Where**: RFC 0002 § 3.3 "A tool MUST NOT modify an `authored` node" (sub-files carry no hash, SPEC § 4); § 5.1–5.2 "A node with media showing the character carries an age" (depends on the author writing `who: [{identity: self, shown: true}]`; the validator cannot know who is in the picture); § 4.2 `fidelity` "a renderer … MUST NOT 'upgrade' one"; § 4.6 "honours `disclosure`"; RFC 0003 § 3 "`relations` do not vary by preset" (nothing to check).
- **What**: SPEC § 11.1 has a list "Requirements a program cannot check … they bind the author"; the RFCs add several such requirements without saying where they land.
- **Fix**: add one sentence per RFC: "The following bind the author or the host and are not checked: …", and say that `who[].shown` with `identity: "self"` is the declaration the validator relies on.

## Summary — the three findings to deal with first

1. **F1 / F2 (BLOCKING, safety)**: the validator's explicit-content rules are keyed on `who[].shown` and on the node's own `explicit`, so an intimate image is reachable through `media_from` from a non-explicit node listed in a 12-year-old preset, and an explicit node with no declared person and no age validates in any adult preset. Both reproduced on the fixture with zero diagnostics. RFC 0002 § 4.5's "inherits nothing else" is what opens the first hole; § 5.4's "unknown age never counts as adult" is not applied in the second.
2. **F3 (BLOCKING, doc vs code)**: RFC 0003 § 6 says a 1.0 file using the new identity fields gets a *warning*; the validator, its test and the CHANGELOG make it an *error*, and RFC 0002 makes the same situation an error. One severity, stated once.
3. **F8 (SHOULD, consistency)**: the moment/period membership and `after` semantics are stated three ways (§ 3.2, § 4.3, § 6.1/6.5), the RFC's own example (`ev2` at 28 `after` the 24–28 period, inclusive bounds) is a case § 6.1 says to warn about, and the "`after` contradicting dates" / "different birth years" / `memory-timeline` findings announced for `cof validate` and the coherence API exist only in the builder. Define *inside* and *contradicts* precisely, decide whether `part-of` is the exception or the normal attachment, and make § 6.1 list what the validator actually does.
